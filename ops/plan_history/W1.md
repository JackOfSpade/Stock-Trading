## H-W1-02 — CATALYSTGATE MODE — REDUCED DEPTH PER CANDIDATE, KEYED ON SPENTBYGATE ARITHMETIC (added 20260914, owner direct

_Moved verbatim from `Claude_Task_Plan.md` (W1, was line 3410) on 2026-10-30. Historical record only; the binding rule is the condensed text in the plan._

**CATALYST-GATE MODE — REDUCED DEPTH PER CANDIDATE, KEYED ON SPENT-BY-GATE ARITHMETIC (added 2026-09-14, owner directive; implements the condition the RESEARCH-COST TENSION paragraph below laid down, and is the analysis-side half for A of what W2's INDEX MODE is for B).** PART 2A spends full (a)-(e) research on 30-50 candidates every week regardless of whether any of them can still be actionable when A next opens. This mode reduces that per candidate. It NEVER drops a candidate and NEVER skips on router state alone.
   - **STEP 1 — derive the GATE DATE, every cycle, and show the arithmetic (rewritten by Rev 52, owner directive 2026-10-22, interactive session).** The gate date is A's next REACHABLE `M1a`/`M1b` re-score. Rev 52 made Strategy.md's `### Shock / overlay grading rubric` symmetric and fast in both directions, with no quiet window and no retracement dwell, so every scheduled re-score is reachable, and an out-of-cycle one is reachable as soon as D2a queues a refresh (its REFRESH REQUEST, on any D2 item 4 trigger in either direction), or is already due once D2 has serviced or logged (refresh-only) a trigger D2a has not yet turned into one. **The gate date is the EARLIEST of (a), (b) and (c), each shown in the arithmetic (inputs (a) and (c) rewritten as a review fix, Rev 52, owner directive 2026-10-22, interactive session).** (a) **The next scheduled M1a/M1b re-score.** `ops/cadence.yaml` schedules M1a on the `monthly first_trading_day` (its trigger fires on the 1st) and M1b after it (`depends_on: [M1a]`). Read `SELECT COUNTIF(routine = 'M1a') AS m1a, COUNTIF(routine = 'M1b') AS m1b FROM ops.run_log WHERE routine IN ('M1a', 'M1b') AND status = 'completed' AND run_date >= DATE_TRUNC(<today>, MONTH)`. Count the completed `M1b`, whose dependency gate implies M1a: the month's re-score is the M1a/M1b pair, and a completed M1a alone leaves its M1b half pending (review fix, Rev 52, owner directive 2026-10-22, interactive session). If `m1b >= 1`, (a) = next month's first trading day per `state.market_calendar`. If `m1b = 0` and today is on or before this month's first trading day, (a) = this month's first trading day. If `m1b = 0` and that day has passed, a catch-up is pending, so (a) = today (fail open). Show `m1a` and `m1b` in the STEP 1 arithmetic and the run note. Test the completed runs, never the presence of a `FUNDAMENTAL_AXIS` row, because M1R writes M1a-shaped rows too. (b) **The `due_date` of any open `PENDING_REGIME_REFRESH` `regime-refresh` item:** `SELECT item_key, due_date FROM state.open_queue_detail WHERE queue = 'PENDING_REGIME_REFRESH' AND item_type = 'regime-refresh'`. (c) **A refresh D2a is already due to queue.** Run D2a's REFRESH REQUEST detection query (D2a Step 0, REFRESH REQUEST) verbatim: it returns each `router-review` entry carrying `fields.measured_trigger` inside its look-back window with no `regime-refresh` queue row counting at or after that entry's `logged_ts` (a covered close counts at its covering snapshot's cut instant, `payload.covered_by_snapshot_ts`). If it returns a row and (b) found no open item, (c) = the date of D2a's next run, which is the `due_date` the item it writes will carry (D2a fires Sunday to Thursday at 16:40 MT per `ops/cadence.yaml`, so for W1's Sunday 01:30 MT slot that is the same day). Otherwise (c) does not apply. State all three inputs and the derived date. **The pre-Rev 52 derivation is RETIRED and must not be run:** this step used to read `state.rerisking_limb_status` and step past any scheduled re-score the rubric's price leg (the 50% Brent retrace) and quiet-clock leg (15 trading days clear of the most recent qualifying shock-cluster member) both held `acute` through, which is how the 2026-W37 `Watchlist.md` cycle note put the gate at 2026-11-02 with 2026-10-01 unreachable on both legs. Neither leg exists any more, so never skip a scheduled re-score on the ground that the rubric would hold `acute` through it, never compute a quiet clock, and never read the retired view. The two refinements of the quiet-clock leg lapse with it: the 2026-10-18 pin that measured a cluster member's Brent move from the curated series rather than D1 prose (alert `4d135348-e6b6-4f90-9423-2b0d261f8534`) and the 2026-10-19 UNRULED SHOCK EVENTS lower-bound / upper-bound derivation (alert `fc7b0e63-9206-48a0-8025-1ebc2e4bda19`); whether an event qualifies is still a scoring's ruling, never W1's, and W1 no longer needs one. STEP 3b's literal does not change and carries the derived date.
   - **STEP 2 — classify each candidate, AFTER the DIRECTION ADMISSIBILITY rail above has run.** A candidate is **`SPENT-BY-GATE`** if and only if it carries a DATED catalyst per (c) AND that date falls strictly before the gate date. Everything else — an undated catalyst (`T`), a catalyst on or after the gate date, or any candidate whose date you could not establish — is **`GATE-SURVIVING`** and gets FULL (a)-(e). Undated is deliberately treated as surviving: you cannot prove a name spent without a date, and the harmful direction here is under-research.
   - **STEP 3 — the reduced depth, and exactly what it does NOT cut.** A `SPENT-BY-GATE` candidate still gets (a) direction, (c) the catalyst date that spent it, (d) the overlap check, and (e) tier — plus a ONE-LINE gap thesis and the literal mark `SPENT-BY-GATE (gate <date>)`. What is reduced is (b): do NOT chase supporting public documents to first-party certainty for a spent name. That is the actual cost this mode exists to cut — MEASURED: the ORCL earnings date was chased across FOUR consecutive W1 cycles and resolved to first-party certainty (Oracle's own 2026-09-02 "Sets the Date" release) for a 2026-09-10 catalyst landing six days before the earliest date any A epoch could then open. (d) is NOT cut — it is a queue lookup, not research, and it is what stops an already-queued name reading as NEW.
   - **STEP 3b — THE MARK IS A FIXED-FORMAT FIELD ON EVERY TOP-10 / A-CANDIDATE ROW, SO W4 READS IT RATHER THAN PARSES PROSE (added 2026-10-11, W5 SPEC-DEFECT NOTICE INTAKE, closing the W1-owned half of W1's `w4_a_queue_row_catalyst_stale_at_enqueue`, alert `559ee98c-05ff-418a-8488-acd46001c874`; the W4 half landed 2026-09-20 in W4 §D \"CARRY W1's GATE MARK ACROSS THE ENQUEUE BOUNDARY\").** Every candidate row W1 publishes in `Weekly_Catalyst_Calendar.md` ends with exactly one of two literals: `GATE: SPENT-BY-GATE (gate <YYYY-MM-DD>; catalyst <YYYY-MM-DD>)` or `GATE: GATE-SURVIVING (gate <YYYY-MM-DD>; catalyst <YYYY-MM-DD|undated>)`. The `GATE-SURVIVING` literal is new — STEP 3 previously required a literal only for the spent case, so a W4 session could not tell \"surviving\" from \"not classified\" without re-deriving the gate. W4 §D copies that literal verbatim into the A-queue row's context, which is what makes a stale catalyst self-declaring on `state.open_queue`.
   - **STEP 4 — the gate MOVES, so a spent name is spent for THIS cycle only.** A refresh for a trigger D2 services or logs after this run (on any trigger, in either direction, since Rev 52) opens an earlier re-score this run could not see; one D2 serviced or logged before this run is already input (c). A drained item moves the gate back to the scheduled one. Re-derive the gate date from scratch every cycle and re-classify every candidate against it — never carry a prior cycle's `SPENT-BY-GATE` mark forward. A name reduced this week gets full (a)-(e) next week if the gate moved behind its catalyst. Recording the catalyst date in the mark is what makes that promotion mechanical rather than a re-read.
   - **FAIL OPEN, ALWAYS.** If `state.open_queue_detail`, `ops.run_log` or the REFRESH REQUEST query behind input (c) is unavailable, the next scheduled re-score date cannot be established, or the gate date cannot be derived for any reason, run FULL (a)-(e) on EVERY candidate and say so in the run `<note>`. (The narrower UNRULED-events case added 2026-10-19 under alert `fc7b0e63` was retired by Rev 52, owner directive 2026-10-22, interactive session, together with the quiet-clock leg it served.) This mode may only ever REMOVE work on a candidate provably out of reach; ambiguity resolves toward more research, never less. Likewise if A's `STRATEGY_ACTIVATION` reads **ACTIVATE**: there is no gate, so there are no spent names and the mode is inert.
   - **REPORT IT, so the saving and the correctness are both auditable.** In this run's `<note>`: the derived gate date, the inputs behind it ((a) the next scheduled re-score date with the completed `M1a` and `M1b` counts it rests on, (b) the `item_key` and `due_date` of any open `regime-refresh` item, and (c) any trigger the REFRESH REQUEST query returned, with the D2a run date it implies), the count of candidates marked `SPENT-BY-GATE`, and the count that survived. A cycle where nearly everything is spent is itself a signal worth seeing — it means the week's catalyst crop sits entirely inside a closed epoch.
   - **This also relieves, without closing, the separate 11-50-tier observation** the RESEARCH-COST TENSION paragraph records: that tier's work is still discarded weekly, but the spent share of it is no longer researched at full depth first. That gap remains open and is not adjudicated here.
