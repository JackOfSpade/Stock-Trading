STEP 2 — FOR EACH MISS, EXECUTE INLINE (bounded). Process at most **N=4** misses per run, **oldest first (`ORDER BY as_of ASC`** — the view's real date column, NOT the compound `miss_key` string, whose mixed daily/period date shapes do not sort chronologically); if more remain, leave them (write NO log row) for the next OPS2 run or OPS0's residual email, and note the deferral in the chat summary — one down-day's backlog must never blow up a single session. For each `(miss_key, routine=X, tier, as_of)`:
1. **SCOPE GUARDRAIL — defense-in-depth.** If X ∈ {D2, D2a, M4, Q4, A3, SL4}, do NOT execute it: the readiness view already excludes these (OPS0's manual alert covers them), so an appearance here means a `bigquery/59` regression — SKIP this row, `CALL ops.sp_raise_alert('warning','OPS2','catchup_executor_scope_violation','<X> appeared in the never-execute list — bigquery/59 exclusion regressed; SKIPPED, fix the exclusion list','<JSON>')`, leave the miss for OPS0's email, and CONTINUE to the next miss. W4 is deliberately executable because its idempotent queue-only research handoff is catchup-safe; its normal slice and the order-craft scan below remain binding. (A `warning`, not a `critical`: OPS2 already averted the danger by skipping, and a catch-up config regression is not a capital emergency that should flip the trading-halt gate — `state.trading_enabled` halts on any open non-excluded critical.) Never treat absence from the exclusion set as license to run one.
2. **ORDER-CRAFT SLICE-SCAN — a routine that crafts orders must never be run by OPS2.** Grep ONLY routine X's OWN section of `task_plan/X.md` for `create_order_instruction` / `delete_order_instruction` — **never the whole file**: every generated slice is prefixed with the shared preamble (Human role / IBKR connector usage / FILE CONVENTIONS, etc., identical across every routine), which itself references both strings repeatedly and would make a whole-file grep a false positive for EVERY catchup_safe routine — defeating this scan (and OPS2 itself, which would then defer everything) entirely. Isolate X's own section first — X's own `## X.` heading is always the LAST `## ` heading in its generated slice (nothing else follows it), so `sed -n '/^## X\./,$p' task_plan/X.md` captures X's body and nothing of the shared preamble above it — THEN grep that isolated text for the two strings. If present there, X crafts orders — the notable case is **D3**, which is `catchup_safe` yet order-crafting (its persist-and-wait DAY re-craft + GO-WITHOUT-ORDER re-stage call `create_order_instruction`), so it is NOT in the STEP 2.1 value-based set but still must not be inline-run. DEFER it: write NO `ops.catchup_refire_log` row, note "deferred:order-crafting", leave it for OPS0's 22:30 email (an operator re-runs it via its own trigger), and CONTINUE. This slice-scan self-maintains the exclusion from X's OWN section of the actual slice text (never the shared preamble), so a future catchup_safe routine that gains an order-craft step is caught automatically rather than silently mis-executed — and a routine that does NOT craft orders is never false-flagged by preamble boilerplate.
3. **IN-FLIGHT + IDEMPOTENCY RE-CHECK** (immediately before executing, mirroring OPS0 STEP 2 / the ACTIVE-REPAIR pattern): re-read `ops.run_log` for X/today — if a `'completed'` row now exists (X finally ran, or was already caught up), SKIP; if a `'started'` row within the last 3 h with no terminal row exists (X is in-flight / mid-dependency-wait), SKIP. Re-check `ops.catchup_refire_log` for the tier-aware `miss_key` — if any row exists, SKIP (already attempted). These re-checks close the execute-vs-late-original and double-executor races exactly as OPS0's do.
4. **CONNECTOR CHECK.** Confirm OPS2 has, live and authed, every connector X's slice needs to run. If any is absent/unauthed, DEFER — leave the miss in readiness (write NO `ops.catchup_refire_log` row) so OPS0's email surfaces it, note "deferred:connector", and continue.
5. **EXECUTE X INLINE — at X's FULL fidelity, in OPS2's OWN branch.** Read `task_plan/X.md` and PERFORM X's steps EXACTLY as written, running X as X would run itself: honor X's own gates, blinding, scope, and run-logging. Three hosting requirements: **(a) NO MODEL DOWNGRADE** — OPS2 runs on the same model the routines use (`claude-opus-5-5`); execute X's judgment-heavy steps at that fidelity, NOT on a weaker sub-agent model — a caught-up M1a regime score or A1/A2 re-derivation must be indistinguishable in quality from its own on-time run. Use isolated sub-tasks for context/fan-out only where X ITSELF would, never to downgrade the model. **(b) SAME BRANCH, NOT AN ISOLATED WORKTREE** — X's file writes (`Daily.md`, `Weekly_*.md`, research outputs) and commits must land on OPS2's OWN session branch (which publishes through its own selected PR and confirmed main landing exactly as X's own branch would), so X's durable output actually reaches `main`; do NOT host X in an isolated worktree whose commits OPS2's session-end push never touches. **(c) RUN-LOG IDENTITY** — X's own slice logs `ops.sp_log_run('X', <today, America/Denver>, 'started'/'completed', ...)` — **`run_date` is ALWAYS TODAY, NEVER `<as_of>`/`period_start`** (corrected 2026-08-19; this sub-bullet previously read `<as_of>`, contradicting the "honor X's own run-logging" clause one sentence earlier — every routine's own generated slice hardcodes `sp_routine_start('<ID>', <today, America/Denver>, ...)`, and `<as_of>` belongs to `ops.catchup_refire_log.miss_key`/`tier` and to STEP 2's oldest-first ordering ONLY). Three things key off `run_date = today` and all three break under a `period_start`-stamped row: X's own SAME-DAY DOUBLE-RUN GUARD, item 6's completion-verification query below, and `bigquery/90`'s in-flight guard (which is what would let OPS0's 22:30 sweep email an actionable "re-run manually" alert for the very routine OPS2 is mid-flight on — the `catchup_executor_headroom` finding). `bigquery/184` now also matches that guard on routine alone so it no longer depends on this convention being transcribed correctly, but log TODAY regardless — the other two consumers have no such backstop. `<instruction>` = X's OWN verbatim canonical trigger string ("Read Claude_Task_Plan.md. Perform <X>...") so `state.routine_last_instruction`'s `LIKE 'Read Claude_Task_Plan.md. Perform %'` filter matches; OPS2's hosting context goes in `<note>`, not `<instruction>`. Run this hosting orchestration (X's SAME-DAY GUARD + run-logging) in OPS2's OWN orchestrating context FIRST, before decomposing any of X's later steps into sub-tasks — never delegate X's guard/logging to a context-poor grunt sub-agent. Let X's slice self-log; rely on X's own SAME-DAY DOUBLE-RUN GUARD to no-op cleanly if X in fact already ran.
6. **RECORD THE CATCH-UP — only after VERIFYING X truly completed.** Before writing the durable suppression row, EXPLICITLY query `SELECT COUNT(*) FROM ops.run_log WHERE routine='X' AND run_date=<today, America/Denver> AND status='completed'` (TODAY, matching what item 5(c) requires X to log — NOT `<as_of>`; a `period_start`-keyed lookup here would find nothing for a catch-up that in fact succeeded and would wrongly route it to item 7. The miss itself would still clear — `state.cadence_period_watch.ran_completed_this_period` is a RANGE test, `rl.run_date >= period_start AND rl.run_date <= today`, so ANY in-period completion satisfies it — but you would lose the `ops.catchup_refire_log` audit row and the `catchup_caught_up` info alert, and, because that log row is what suppresses OPS0's sweep, re-expose X to being refired while it has already run) (and confirm X's expected output was committed on OPS2's branch) — do NOT infer completion from a sub-agent's returned "done" summary: a stalled or cut-off sub-agent can report done while X only ever logged `'started'`, and trusting that would durably + PERMANENTLY suppress a genuine miss. ONLY if X actually logged `'completed'`: `INSERT INTO ops.catchup_refire_log (miss_key, routine, tier, trigger_id, outcome, note) VALUES (<miss_key>, 'X', <tier>, <X's trig_id or NULL>, 'caught_up_inline', 'OPS2 executed X inline (headless-RemoteTrigger workaround)')` — the permanent idempotency marker (`state.catchup_refire_readiness` then excludes this `miss_key`, so OPS0's 22:30 sweep does not re-email it) — and `CALL ops.sp_raise_alert('info','OPS2','catchup_caught_up','<X> auto-run inline for <as_of> (previously missed) — no action needed','<JSON: miss_key, routine, tier, as_of>')` (info only, audit trail, never a chat question). If the verification query shows NO `'completed'` row, treat it as an execution failure (item 7).
7. **ON EXECUTION FAILURE OR UNVERIFIED COMPLETION.** If executing X errors, or X's own gate legitimately halts it (e.g. a genuine trading-halt inside X), or item 6's verification finds no `'completed'` row, do NOT write a false `'completed'` for X and do NOT write a `'caught_up_inline'` log row — leave the miss visible so OPS0's residual email surfaces it for a human, record OPS2's own note with the error (+ the `INCIDENT`/`DEPWAIT` token if applicable), and continue to the next miss. A failed or unverified inline execution MUST degrade to the manual-email path, never silently mark a miss resolved.
