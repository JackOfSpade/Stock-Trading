## H-D3-08 — OPS0 WATCHDOGFALLBACK (resilience audit 20260716 — who watches the watcher: OPS0 rides the same trigger platfo

**OPS0 WATCHDOG-FALLBACK (resilience audit 2026-07-16 — who watches the watcher: OPS0 rides the same trigger platform it guards, and cadence_check's missed_run alert for it is email-only; check corrected 2026-08-08 for the Fri/Sat daily-tier schedule change — see below).** Using `state.trading_day_today.today`, first resolve OPS0's LAST EXPECTED firing day — **not literal calendar-yesterday.** `DATE_SUB(today, INTERVAL 1 DAY)` was correct only while OPS0 (like D3 itself) ran every calendar day; once the daily-tier fleet, OPS0 included, stops firing Friday and Saturday, a D3 run on Sunday checking literal yesterday would check Saturday — a day OPS0 never runs BY DESIGN under the new schedule, not a miss — and this fallback would false-fire "OPS0 missed" every single Sunday, forever, exactly the false-positive class this bullet exists to avoid. Derive the last EXPECTED day from the calendar mechanically instead of hardcoding a day-of-week list:
```sql
SELECT MAX(cal_date) AS ops0_last_expected_day
FROM UNNEST(GENERATE_DATE_ARRAY(DATE_SUB(today, INTERVAL 7 DAY), DATE_SUB(today, INTERVAL 1 DAY))) AS cal_date
WHERE EXTRACT(DAYOFWEEK FROM cal_date) NOT IN (6, 7)   -- exclude Friday(6)/Saturday(7); BigQuery DAYOFWEEK 1=Sunday..7=Saturday, same convention as bigquery/09_market_calendar.sql:110
```
then `SELECT COUNT(*) FROM ops.run_log WHERE routine='OPS0' AND status='completed' AND run_date = <ops0_last_expected_day>`. On every day OTHER than Sunday this reduces to the original `DATE_SUB(today, INTERVAL 1 DAY)` (Mon–Thu's calendar-yesterday is never Fri/Sat, so the exclusion never changes the answer) — the fix only bites on Sunday but is expressed generally, off the actual skip-day set, so it needs no future edit if that set ever changes. If OPS0 has EVER logged a completed run (self-bootstrapping guard, same convention as `state.cadence_watch.monitored`) AND that count is 0: perform OPS0's STEP 1 and STEP 2 inline, verbatim per that routine's own text (read `state.catchup_refire_readiness`, re-fire each row via `ops/trigger_ids.json` + `RemoteTrigger run`, write the same `ops.catchup_refire_log` rows and per-row alerts — the miss_key idempotency makes this safe even if a delayed OPS0 later runs tonight), with ONE exception: if a row's `routine` is `D3` itself, do NOT call RemoteTrigger (this very session IS the recovery run) — just `INSERT INTO ops.catchup_refire_log (miss_key, routine, tier, outcome, note) VALUES (<miss_key>, 'D3', 'daily', 'refired', 'self-recovered inline — D3 fallback session supersedes')` so the miss_key is closed without spawning a redundant second D3 session. Then `CALL ops.sp_raise_alert_once('warning','D3','ops0_missed_fallback','OPS0 did not complete on its last expected day — D3 ran the catchup sweep inline; check OPS0\'s trigger','<JSON: missed_date=ops0_last_expected_day, rows_swept>')`. **CLEAR LIMB — the OTHER branch of the same count, and the ONLY thing that ever closes this category (added 2026-09-21; policy row `bigquery/245_ops0_missed_fallback_policy.sql`).** If that same `COUNT(*)` is **greater than 0** — OPS0 did complete its last expected day — then before moving on, close any notice left over from a previous miss: `UPDATE ops.alerts SET resolved = TRUE, resolved_ts = CURRENT_TIMESTAMP(), resolved_note = CONCAT('auto-resolved by D3: OPS0 logged a completed run for its last expected day ', CAST(<ops0_last_expected_day> AS STRING)) WHERE category = 'ops0_missed_fallback' AND NOT resolved` — scope by category here rather than `alert_id` because every open row of this category reports the same single condition (OPS0 is not completing) and that condition has just been measured false; there is no per-row state to preserve. **WHY THIS EXISTS: until 2026-09-21 nothing in the entire fleet could close this category.** A repo-wide grep for `ops0_missed_fallback` returned exactly two hits, this raise site and its generated `task_plan/D3.md` mirror — no `UPDATE` anywhere, no `ops.alert_policy` row, and no arm in `ops.sp_auto_resolve_alerts`, which per that table's documented semantics means a category absent from it is latching by construction and the generic resolver can never touch it.
