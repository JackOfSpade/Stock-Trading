## 1. Human Operator Interaction Protocol (HOIP)

**Canonical-current text:**

The human operator's role is execution, not decision-making.

The human operator does effectively one thing:
1. **Confirm a crafted order.** Claude crafts the exact order through the IBKR connector (`create_order_instruction`) and surfaces a tap-to-confirm deep link; `create_order_instruction` itself also fires IBKR's own order-created notification to the human operator, so no calendar event is created for a craftable order (2026-07-09 — redundant with that notification, and the operator confirms immediately regardless; see Claude_Task_Plan.md "Calendar MCP usage"). The human operator opens the link, reviews the pre-filled order in IBKR, and confirms it (or declines). The human operator never types ticker, side, quantity, price, order type, or duration — Claude crafts all of them. **Craftable now includes single-leg options and OPT–OPT combos/spreads** (self-improvement audit ITEM 13, 2026-07-11 — `create_order_instruction`'s own tool documentation confirms STK/FUT/OPT/FOP single-leg plus OPT–OPT combos are supported; the repo previously, incorrectly, documented options as connector-uncraftable). For the security types the connector genuinely still cannot craft (mixed-type combos, FOP/FUT combos, or any structure `get_combo_identifier` rejects), Claude falls back to a text order block the human operator enters manually, explicitly labeled as a manual-entry fallback and **carried in a `[Claude] Confirm order` calendar event** in place of the deep link — never chat-only, since routine chat is unmonitored and there is no `create_order_instruction` call to trigger an IBKR notification for this case (Claude_Task_Plan.md "Calendar MCP usage").

All analytical work — thesis construction, position reviews, research-deferral checkpoints, re-screens, foundation-change and constraint-relaxation reviews, router reviews — runs autonomously: in-session in the triggering routine, or via the `Pending_Analysis.md` queue drained daily by D2. The operator is never asked to paste an analysis prompt into a fresh chat.

**Source-content manipulation is NOT caught by the confirm-tap — the mechanical kill triggers are the backstop (self-improvement audit ITEM 19, 2026-07-11).** The confirm-tap above is a real execution gate (fat-finger / malformed-order protection: `create_order_instruction` genuinely cannot execute without it) but a deliberately BLIND decision gate — HOIP strips chat to the order line only, so a thesis built on a manipulated or hallucinated external fact would produce a well-formed order that passes the tap unchallenged. `AI_Trading_Foundation.md` disadvantage 2.10 concedes this directly: "residual risk is in source-content manipulation of consumed research reports and financial documents, which remains unmitigated at the model level." As with disadvantages 2.13 (miscalibration) and 2.19 (look-ahead contamination), the compensating control is process, not human review: `Claude_Task_Plan.md`'s **External-content extraction discipline** requires every externally-sourced claim to pass through a narrow extraction step before it can enter thesis reasoning, and — the real backstop — any position built on a bad thesis still has to survive the SAME drawdown / gate / m2m mechanical kill triggers as every other position. Do not route this concern through the confirm-tap; it was deliberately stripped of reasoning context by HOIP and that is not being reopened.

Three prior actions are retired:
- **Screenshotting IBKR is obsolete.** Claude reads the human operator's positions, balances, live orders, executed fills (with exact price/commission/realized P&L), and live + historical market data directly through the IBKR connector (§11). Claude never asks for a screenshot.
- **Persisting Claude-produced files is obsolete.** Claude routines write project files directly.
- **Pasting analysis prompts into fresh chats is obsolete.** Thesis construction and every other Claude-only analysis step run in-session or via the autonomous `Pending_Analysis.md` queue — never as a human-pasted calendar event.

The human operator does NOT verify commissions, make EV decisions, monitor markets intraday, watch sell-side wires, parse earnings prints in real time, decide execute-vs-skip on staged orders, decide override-vs-honor on NO-GO recommendations, choose convergence targets, position sizes, limit prices, or invalidation criteria, or read project sources to understand context Claude could resolve internally.

If a workflow requires the human operator to do anything beyond confirming crafted orders, that workflow is broken and Claude redesigns it before staging anything.

**Claude resolves all decisions internally.** Claude makes every decision the framework requires — execute or skip, GO or NO-GO, target selection, sizing, timing, invalidation criteria, and (rev 2026-07-10 — Strategy Arsenal autonomy conversion, owner directive) **strategy adoption, retirement, and restart** via the Strategy Arsenal Lifecycle (§18) — without human operator input. The human operator's *judgment* is never solicited: Claude does not ask whether to place a trade; it resolves GO/skip itself and surfaces only the crafted order. The tap that confirms a crafted order to IBKR is the human operator's *execution* role — the physical act of placing the order — not a decision the human operator is being asked to make. If a decision genuinely cannot be made without information Claude does not have, Claude defers it to a future autonomous routine — a `Pending_Analysis.md` queue entry (drained daily by D2) with a `due_date` set to when the missing information will be available, and a conservative-default fallback. Claude documents the deferral logic in Decision_Log.md so the future routine can resume.

**Sell-side and follow-on data monitoring is Claude's responsibility.** Claude does not stage workflows requiring the human operator to "watch" anything. Where follow-on data (e.g., a peer print landing two days after entry) could affect a position, Claude uses autonomous review routines (a `Pending_Analysis.md` queue entry drained daily by D2) to handle it — no human action.

**Chat output discipline.** Claude's chat output to the human operator contains only:
1. The order(s) to execute — surfaced as crafted IBKR order instructions (the tap-to-confirm deep link plus a one-line human-readable summary `SIDE QTY TICKER TYPE TIF` — `TYPE` is always `MARKET`, market-only owner directive 2026-07-21), or `no order` — AND
2. The minimum information the human operator needs to confirm a crafted order.

Claude's chat output does NOT contain: recapitulation of decision reasoning that already exists in `events.decision_log` (the retired Decision_Log.md/Portfolio_Ledger.md are BigQuery now, §15), adversarial-review summaries, pillar/criteria walkthroughs, "three things to flag" framings, pending-queue summaries beyond what affects the human operator's next action, theater-checks, compaction-survival notes, explanations of why a NO-GO is a NO-GO, operator-override paths when the recommendation is NO-GO.

**Project sources are for Claude, not for the human operator.** Everything Claude writes to project sources — `events.decision_log`, Daily.md, the factbase/methodology files, and the other cadence-working files (the retired Decision_Log.md/Portfolio_Ledger.md live-state files are BigQuery now, §15) — is written for future Claude sessions. The human operator does not read these files and no longer persists them — Claude routines write project sources directly (the prior "persist Claude-produced files" action is retired). Claude writes for self-comprehension at compaction-survival depth, NOT human-operator-facing summaries.

**Self-check Claude runs before each chat response:**
- Have I created any new task for the human operator beyond confirming a crafted order? (Analysis is autonomous — never ask the operator to paste an analysis prompt.)
- Have I asked the human operator to make any decision, or to take a screenshot (screenshots are obsolete — read the connector instead)?
- For every staged equity/ETF order, did I craft the order instruction (`create_order_instruction`) and surface its deep link, rather than emitting a raw text block the human must type?
- Have I included prose in chat that summarizes context already saved to project files?
- Have I deferred a decision to "human-operator's call" that I should have resolved myself?

If any answer reveals a violation, the response is revised before sending.

## 3. NO-GO Records Are Context, Not Barriers

**Canonical-current text:**

A prior NO-GO disposition for a name does NOT auto-fail a future thesis on the same name. Each fresh trigger event (new earnings print, fresh post-event window, new catalyst, new information layer) merits fresh thesis-construction evaluation against the relevant strategy's entry criteria. The prior NO-GO record is one input to the new evaluation — context, not barrier — but does not artificially inflate the threshold to enter.

This rule applies symmetrically across strategies: a prior Strategy D NO-GO does not propagate as a barrier for a Strategy C or B entry on the same name (the strategies have different mechanisms); a prior Strategy B NO-GO on one event does not gate a Strategy B re-evaluation on a structurally distinct subsequent event (e.g., AXSM 2026-05-02 FDA-approval criterion-1 NO-GO did not gate AXSM 2026-05-04 Q1-print criterion-4 NO-GO; each is a separate event with its own 10-day post-event window).

The cost of occasional wasted thesis-construction work on structurally-closed names is accepted; the benefit of preserving framework integrity (no Closed_Names.md style permanent gate) is paramount.

**Revision history:**
- (foundational): Implicit from experiment inception; framed explicitly across multiple Decision_Log entries (2026-04-26 D outcome GOOGL precedent; 2026-04-27 GOOGL C precedent; 2026-05-04 AXSM Q1-print precedent; 2026-05-03 lifecycle-architecture entry naming the rule). No standalone protocol-introduction entry; rule emerged from operating practice and is authoritative as of 2026-05-03 factbase-architecture session.

## 4. Pre-Mortem Cycle Turn-Batching

**Canonical-current text:**

Pre-mortem adversarial review runs entirely through the autonomous two-routine review pipeline — there is no human-orchestrated, user-pasted attacker loop (rev 2026-07-10 — Strategy Arsenal autonomy conversion, owner directive; supersedes the rev-14 user-pastes-attacker turn-batching this section formerly described). Each cycle is driven by queue-driven routines against `events.queue_events` / `state.open_queue`:
1. **AR_att** (strict-blinded attacker, fresh context, reads ONLY the artifact under review + `trigger_context`) appends its attack to `events.adversarial_reviews` and sets status `attacker-complete`. The BigQuery row is the sole durable transcript; it creates no `Adversarial_Review_*.md` file.
2. **AR_orc** (orchestrator, depends on AR_att) reads the one current attacker row matching the queue item's `(review_id, cycle_number, role='attacker')`, then reads the artifact under review, performs the independent review, applies the mechanical tier triage (§5), self-certifies the theater-check, answers the forcing question in writing, and appends the binding verdict to `events.adversarial_reviews` / `events.decision_log`. It never receives a filesystem output-path handoff.
3. On **REVISION REQUIRED**, AR_orc enqueues an **SL2 auto-revision task** — SL2 redrafts only the flagged Tier-1 defects, re-derives any changed parameter fresh, increments `cycle_number`, and re-enqueues — so the revision is a routine action, never a user turn (this overturns the former "revision reserved to the participant" gate). On **SUFFICIENT**, `state.strategy_adoption_readiness` clears and SL5 registers the strategy into SHADOW (§18).

No step waits on a user to paste attacker output, run an attacker incognito, or confirm a strategy-design change. The compensating control for this autonomy is the full graduation pipeline (adversarial pre-mortem → SHADOW → PAPER → PROBE → 30-trade gate) in §18; and because routine chat is unmonitored (ops/RUNBOOK.md §36) a chat confirmation turn would be a dead end. The former **Exception** requiring explicit user confirmation for a strategy-design change is therefore removed — strategy-design changes now flow through the arsenal lifecycle.

- 2026-04-25: Adopted. → Decision_Log 2026-04-25 "Operational decision: pre-mortem cycle turn-batching".
- 2026-07-10: Canonical text rewritten from the human-orchestrated user-pastes-attacker turn-batching loop to the autonomous AR_att/AR_orc + SL2 auto-revision pipeline; the strategy-design-change confirmation Exception removed. ## 5. Deployment-Risk Stop + Forcing Question (Adversarial Review Cycling)

**Canonical-current text:**

Substantive protocol lives in Experiment_Parameters.md rev 15 (immutable). It runs autonomously inside the **AR_orc** routine on every review — including the new `strategy-adoption` type (§18) — with no orchestrating human session (rev 2026-07-10 — Strategy Arsenal autonomy conversion, owner directive; actor reframed, substance unchanged). Summary for cross-reference:

1. **Deployment-risk stop (pass condition 1(b)).** AR_orc may invoke saturation acceptance when remaining Tier 1 items pass four screens: (i) do not contradict any specific quantitative claim the artifact makes about its own loss-bounding, (ii) do not omit a top-five AI_Edges disadvantage from req-4 enumeration, (iii) do not introduce or leave in place a trigger that fails to detect the failure mode it nominally exists to detect, and (iv) do not break self-containment for a numbered requirement.

2. **Forcing question (mandatory pre-cycle assessment).** Before a cycle continues, AR_orc must explicitly answer in writing (to `events.decision_log`): "If we accept the artifact at its current revision with these residual Tier 1 items, would that change deployment risk vs. fixing them first?" Answer must be (a) yes-continue / (b) marginal-stop / (c) no-stop with substantive reasoning. A continue enqueues an SL2 auto-revision task (§4); it never routes to a human.

3. **Cycle-count soft cap.** Starting at cycle 5, AR_orc must explicitly justify continuation in `events.decision_log` rather than defaulting through "stop conditions don't fire"; beyond the soft cap without justification the candidate is abandoned to REJECTED (§18). Burden of proof shifts after cycle 5.

4. **Mechanical tier triage.** Tier-1/2/3 assignment on each cycle is done by AR_orc mechanically, applying the rev-15 working definitions, and logged to `events.decision_log`; the triage is deliberately NOT itself adversarially re-reviewed (or the loop regresses infinitely). This absorbs the former participant-with-Claude triage step (Experiment_Parameters.md:412) with no human in the loop.

**Read alongside `analytics.calibration_shrunk` (self-improvement audit S-2/B-2, 2026-07-03).** This 3-trade ladder is a narrative precedent set, not a statistical estimate — it can read as more settled than 3 anecdotes support (the exact narrative-overfit risk 2.13/2.4 flag). This does not replace the ladder's qualitative reasoning — it is a cross-check against over-updating on 3 correlated data points.

**Daily.md scan labels** (e.g., "highest conviction" within a watchlist) are local to the scan's relative ordering and do NOT translate to absolute conviction; thesis-construction sessions apply Strategy B's actual entry criteria with absolute-scale calibration.

## 9. Deferral Discipline (No Re-Deferral; Decide-at-Earliest-Resolvable Window)

**Canonical-current text:**

When a decision cannot be made because required information is genuinely missing, Claude defers to a future autonomous routine — a `Pending_Analysis.md` queue entry (drained daily by D2) with a `due_date` set to when the information will be available. Two rules:

1. **No re-deferral (no deferral chaining).** If the future session also cannot resolve, Claude does NOT defer again. The conservative-default fallback is documented in the original deferral entry and fires automatically at the next checkpoint.

2. **Decide at the earliest resolvable information window.** If multiple checkpoint sessions are scheduled and the earliest one has sufficient information, Claude resolves there and cancels the later events as redundant (e.g., HCA criterion (iv) UHS Apr-27 AMC parsed Mon evening rather than Tue 9:25 AM ET; Tue event cancelled).

**Apply pattern**: gate-failure entries document branch (a) clear / (b) single-deferral-with-conservative-default. Branch (b) cannot fire twice on the same gate.

- 2026-04-28 (Tue): Pattern established via HCA criterion-(iv) Mon-evening resolution + Tue 9:25 redundant-event cancellation. → Decision_Log 2026-04-28 "HCA fill captured; Apr 28 SGOV cycle reconciled" compaction-survival note (e).
- 2026-05-04 / 2026-05-05: Pattern reinforced via META Funds-on-Hold gate (b) single-deferral Mon → Tue (a) clear; conservative-default fallback would have fired at Tue if also blocked.

Claude must **never invent a total concurrent position cap** for any strategy unless that cap is explicitly stated in Strategy.md for that strategy. Operational habit, portfolio monitoring convenience, or analogy to a different strategy's cap are not sufficient grounds to introduce one.

## 11. IBKR Connector Protocol

**Canonical-current text:**

An IBKR connector (MCP server) gives Claude routines direct, authenticated access to the human operator's live brokerage account and market data. It is identified by its tool names, not by a server ID (the server ID is not stable across sessions). The tools:

- **Order instructions (the click-to-confirm execution path):** `create_order_instruction` (crafts a saved order and returns `{id, url}` where `url` is a deep link the operator taps to review-and-confirm in IBKR), `get_order_instructions` (lists pending crafted instructions), `delete_order_instruction` (cancels a pending instruction). **Stocks, ETFs, Futures, single-leg Options (OPT), single-leg Futures Options (FOP), and OPT–OPT combos/spreads** (self-improvement audit ITEM 13, 2026-07-11 — corrected from a prior "Equity and ETF only" mischaracterization; verified against the tool's own documentation). Multi-leg equity-option combos resolve via `get_combo_identifier` (OPT legs only) before `create_order_instruction`. Mixed-type combos, FOP/FUT combos, and any structure `get_combo_identifier` rejects remain non-craftable — manual-entry fallback below.
- **Live account state (replaces screenshots):** `get_account_summary` (net liquidation, buying power, available funds, margin, day-trades-remaining), `get_account_positions` (per-position qty / market price / market value / unrealized P&L / `contract_id`), `get_account_balances` (cash + market value by currency), `get_account_orders` (live working orders + fill status), `get_account_trades` (executed fills with exact price, size, **commission**, **realized P&L**, time, and `order_id`).
- **Market data — the operator's IBKR market-data subscription (realtime):** `get_price_snapshot` (live bid/ask, last + timestamp, change, volume, IV, etc.), `get_price_history` (OHLCV bars), `search_contracts` (resolve ticker/name → `contract_id`). Prices are served **realtime on the exchanges the operator is subscribed to** (delayed only where unsubscribed; frozen / delayed-frozen are not served). This is the most accurate live source and is **authoritative over any web or delayed quote** — use it as the primary quote everywhere (CTC verification, convergence checks, market-only order craft, position marks); web quotes are a fallback only when the connector lacks the instrument. **Realtime-awareness:** during RTH a realtime quote has `last.ts` within seconds of "now" and live bid/ask sizes; if `last.ts` is stale or bid/ask returns empty (e.g. pre-market / illiquid), treat the quote as not-live — do NOT market-order into an empty book; defer the craft rather than trading on a stale reference price (owner directive 2026-07-21 — there is no limit price to fall back to). **Prior-close lag (data-quality guard):** `get_price_snapshot`'s prior-/previous-close field can trail the most recent settled session by one trading day, so for any close-to-close (CTC) verification, convergence check, or position mark the **authoritative close is the dated bar from `get_price_history`** — cross-check the snapshot's close against the latest `get_price_history` bar and use the history bar when they disagree (the 2026-06-05 W3 position deep-dive caught `get_price_snapshot` returning the 6/4 close for four names while `get_price_history` had the correct 6/5 close). Query `SMART` (default) for the consolidated best quote; name a primary listing exchange only when a specific venue is required.

**Snapshot-surface outage.** A `get_price_snapshot` tool error is distinct from a structurally valid but non-live quote. Retry one transient-looking snapshot error once with the same request after a short backoff; do not retry a non-transient error. Any failure to obtain a structurally valid snapshot for the instrument being crafted means that quote-dependent MARKET craft is deferred. Probe a liquid unrelated symbol only to classify the failure: if that probe also errors, classify the **snapshot surface** account-wide unavailable; if it succeeds, classify the original instrument as symbol-specific unavailable, but never substitute the probe's price. Leave separately-successful account and history surfaces usable. Never substitute `get_price_history`, a prior close, or a web quote for the live reference that authorizes a MARKET craft — raise a warning identifying `surface=get_price_snapshot`, scope, and the probe symbols, and resume the craft on the next successful snapshot for the target instrument. A snapshot-surface outage does not by itself invalidate fill reconciliation, balances, account snapshots, or dated historical-mark ingestion.

**Execution model — Claude crafts, the human confirms.** `create_order_instruction` does NOT execute a trade. It places a *pending instruction* into the operator's IBKR app that the operator must open (via the returned deep link) and confirm before anything reaches the market. Claude therefore has no execute authority; the operator's confirm tap is the single execution gate. This preserves the experiment's invariant — Claude decides, the human executes — while removing the manual data-entry step (and the operator-discretion limit drift it caused). The deep link opens the operator's full pending-instruction queue, so one tap surfaces every instruction Claude has crafted; per-order calendar events exist for *timing* and a human-readable summary, not because each needs a distinct link.

**Order-craft discipline (market-only, owner directive 2026-07-21; all liquidity/sizing rails stripped 2026-07-22).** When a routine stages an equity/ETF order it: (1) resolves the `contract_id`; (2) pulls a live `get_price_snapshot` (bid/ask, last) and records the live **reference** price (last, or bid/ask mid) — not an order limit; (2a) calls `analytics.fn_order_guard(strategy, side, qty, ref_price, 'MARKET')` — if `passed=FALSE` (not a MARKET order, or non-positive qty/ref-price) do NOT craft; (3) calls `create_order_instruction(contract_id, side, quantity, order_type='MARKET', time_in_force='DAY')` — **no `limit_price` argument is transmitted to IBKR**; the reference price from (2) is instead written into the staged payload's `limit_price` field purely for cash-reservation; (4) writes the returned instruction `id` into the staged-order registry — the `ORDER_STAGED` row in `state.open_orders` (`events.queue_events`) alongside the staged-order details, per the staged-order registry below (§15: there is no Portfolio_Ledger.md; the durable persist-and-wait state is the registry); (5) relies on `create_order_instruction`'s own IBKR notification as the human-facing confirm surface (2026-07-09 calendar-scope narrowing, §1) — a `[Claude] Confirm order` calendar event is created ONLY for a genuinely non-craftable/manual-entry order, carrying the deep link, the `SIDE QTY TICKER TYPE TIF` summary (`TYPE` is always `MARKET`), and the instruction `id`. If a staged order is later cancelled/superseded before the operator confirms, Claude calls `delete_order_instruction` to clear it.

**Entry/exit decision (market-only, 2026-07-21; partial-sell support + rail strip 2026-07-22).** Orders are MARKET orders, so there is no limit price to set, chase, or re-price — the resting-limit RAISE/HOLD/LOWER/ABANDON machinery from the retired 2026-07-20 **LIMIT DECISION** protocol block (Claude_Task_Plan.md preamble, "Crafting an order (equity/ETF)") is retired, along with the >0.5%-off-last equity price-band advisory it fed. At each craft (initial or daily re-craft) the judgment is **ENTER, EXIT, or ABANDON** — not only a binary ENTER/EXIT-NOW-vs-ABANDON: on the exit side, Claude may craft, on thesis/market-conditions judgment, either a full exit or a **partial sell** (a trim / scale-out — a MARKET sell for fewer shares than the full position). A partial sell needs no separate craft mechanics here — the steps above are already side-agnostic, so it is simply a SELL with `quantity` less than the full position; see Claude_Task_Plan.md (D2 multi-tranche exit + D2a `ADJUST` reduce-but-stay-OPEN reconciliation) and Strategy.md (each strategy's per-strategy trim scope) for the mechanics, not restated here. If the thesis still warrants the position (or the trim) within its window and the name clears the ORDER-GUARD CHECK — `analytics.fn_order_guard`'s only rails as of the 2026-07-22 strip: the order must be well-formed MARKET (`order_type=MARKET`, `qty>0`, `ref_price>0`); options additionally require a defined, positive `max_loss` via `analytics.fn_order_guard_options` (see the Revision history entry below) — craft the market order now; otherwise ABANDON (set the registry row terminal, log the conservative default). `entry_window_close`, the STAGING ATOMICITY gate, and the operator confirm-tap still bind unchanged. Every decision — ENTER, EXIT, TRIM, or ABANDON, including a repeated ABANDON — is logged via `CALL ops.sp_log_decision(...)` (`entry_type='entry-decision'`, `decision='ENTER'|'EXIT'|'TRIM'|'ABANDON'`) with the reference price and a rationale.

**Time-in-force is `DAY`, always — never `GTC`.** The connector exposes **no modify/amend endpoint**: a crafted order's price, size, side, or duration cannot be changed in place. The only available actions are `create_order_instruction` (craft new), `delete_order_instruction` (clear a still-pending, not-yet-confirmed instruction), and `get_order_instructions` (read); a *confirmed working order* can be cancelled only by the operator inside IBKR (the connector cannot cancel a live working order). "Modifying" an order therefore always means delete/cancel + re-craft. Given that, **every order Claude crafts — entry or exit, regardless of whether its thesis intends it to rest for days — is `time_in_force: "DAY"`, never `GTC` (and never `OVT`/`OND`/`OPG`).** A persist-and-wait order (an entry or exit whose thesis calls for it to stay live across multiple sessions) is **not** crafted once as GTC and left to sit; it is **re-crafted fresh as a new MARKET order each trading session it is meant to remain live** — day → day → day → filled, rather than gtc → filled. The daily re-craft is the point of the policy, not overhead: every order Claude crafts is `order_type='MARKET'` (owner directive 2026-07-21) with no `limit_price` ever transmitted, so there is no resting limit to re-pull or re-price — each session's `create_order_instruction` is simply the checkpoint at which the ENTER/EXIT-vs-ABANDON judgment (above) is re-run against a live `get_price_snapshot` and, if the thesis still warrants it, a fresh MARKET order is crafted at whatever the market is that session (and since there is no modify endpoint, a resting GTC could only be re-crafted by delete + re-craft anyway, so DAY gives up nothing and forces the daily review). A still-resting order that should persist is re-crafted by the next session's staging-integrity sweep (D2/D3); one whose entry window has closed or whose exit is no longer required is simply allowed to expire at session close. (Operator-discretion duration changes at confirm time are outside Claude's control, but Claude itself never crafts a non-DAY TIF.)

**Staged-order registry — the durable persist-and-wait state (`state.open_orders`).** Because every Claude order is `DAY` (above), a crafted order is *ephemeral*: it expires at session close and is re-crafted fresh, so **between sessions a GO'd-but-unfilled entry (or a resting exit) has no live order or instruction at the broker.** The *intent* to keep that order open must therefore live in durable, queryable state — not in narrative memory. When a routine stages an entry (a thesis GO) or an exit it writes an **`ORDER_STAGED` row to `events.queue_events`** (surfaced as `state.open_orders`) carrying `contract_id` / `side` / `qty` / `limit_price` / `convergence_target` / `time_exit_date` / `entry_window_close` (the row's `due_date`) / the current `instruction_id` / `source_decision_ref` / **`guard_passed` / `guard_reasons`** (self-improvement audit ITEM 15, 2026-07-11 — the `fn_order_guard`/`fn_order_guard_options` result that authorized this craft, embedded so its omission is a detectable fact — `bigquery/scheduled_queries/daily_staging_cap_check.sql` flags a same-day row missing it as CRITICAL; per the 2026-07-22 rail strip (`bigquery/104_strip_pretrade_rails.sql`) the daily-staging-cap backstop now recomputes only the market-only + qty/ref-price sanity verdict from the payload, not a liquidity/sizing check). The `item_key` is **stable across re-crafts** (only `payload.instruction_id` changes); the row is `pending` while the order should remain live and moves to a terminal status (`filled` / `expired` / `abandoned`) only via logged reconciliation. **`pending` is a RECONCILIATION state, not a broker state (clarified 2026-08-03 after a near-miss):** it means "no logged terminal decision has been written for this row yet," NOT "the order is working at the broker" and NOT "the order did not fill." A row that filled at this morning's open stays `pending` until D2a Step 0 reconciles it — the whole overnight block, and every routine in it, sees `pending` on an order that is already filled. Never infer fill state from this field: read `get_account_trades` / `get_account_orders` / `get_account_positions`. The same caveat applies to the staging-time provisional `events.position_events` `cost_basis`, which is a reference-price estimate until that same reconciliation supersedes it. Two mechanisms key off this registry: (a) the normal **persist-and-wait re-craft** — D2/D3 re-craft each ordinary pending row every session its window remains open; and (b) the **§13 cash reservation**. **A MISSING INSTRUCTION IS NOT BY ITSELF EVIDENCE THAT A CRAFT WAS LOST — CHECK FOR A TAPPED ORDER BEFORE RE-CRAFTING (2026-08-26, D3; see the Revision history entry below).** An operator confirm-tap CONSUMES the instruction: once tapped, it converts to a live working order and drops off `get_order_instructions` entirely. So an empty instruction list against a still-`pending` registry row is the signature of a tap just as much as of a lost craft, and the two are indistinguishable from the instruction list alone. Before concluding an instruction is missing and re-crafting it, read `get_account_orders` and look for a working order matching the row (same `contract_id`/ticker, side, quantity); if one exists the row is correctly `pending` and resting, and it **must not** be re-crafted. Only when NEITHER an instruction NOR a matching working order exists is the craft genuinely lost and the re-craft correct. This is the same "the registry is not the broker" reading error as the 2026-08-03 `pending` clarification above, one step further down the chain — and it is capital-affecting in the doubling direction rather than the cancelling one. **Narrow exception:** `item_type='drip-dust-liquidation'` remains registered but is excluded from every generic filled/re-craft/expiry loop; the executable ordinary-row predicate is `COALESCE(item_type,'') <> 'drip-dust-liquidation'` so legacy NULL types are retained. D2a alone reconciles dust by exact instruction id plus aggregate staged quantity and owns its capped retries. Before the connector create, D2a must acquire the pre-seeded singleton `ops.order_stage_mutex` through `ops.sp_acquire_dust_order_mutex` and append a `status='crafting'` registry claim carrying the full dust identity; an item-key precheck is not a concurrency lock because BigQuery primary keys are not enforced. The claim lets the next run recover a process death between connector create and pending-row staging. The mutex is released only after the `ORDER_STAGED` transition or verified failure cleanup. This prevents duplicate full-residual SELLs and coarse unrelated-fill terminalization. A staged order therefore cannot be silently dropped or de-funded; it leaves the registry only by filling or by an explicit terminal decision.

**Dust-claim session binding.** A dust `status='crafting'` payload uses the D2a `ops.run_log.session_id` as
`claim_session_id`, not an unrelated UUID. Recovery joins that exact session id and treats a lone `started` row
older than three hours as the standard dead-run case before considering stale-mutex release.

**`contract_id` discipline.** `contract_id` is the connector's instrument key. Cache each open position's `contract_id` in its BigQuery position record — the `ORDER_STAGED`/`state.open_orders` payload while an order is staged, and `events.position_events` / `state.current_positions` once open (§15: there is no Portfolio_Ledger.md). When in doubt, confirm against `get_price_snapshot`/`get_price_history` before crafting an order.

**Fill reconciliation is connector-driven, not screenshot-driven.** No fill-capture screenshot events are created. Reconciliation is a daily pull (D2a Step 0 as of the 2026-07-09 cutover — D2 no longer owns this; see Claude_Task_Plan.md), idempotent by `trade_id`: read `get_account_trades` over a multi-day window, match fills against the `trade_id`s already recorded in `events.trade_fills`, and for each new fill write the exact price / size / commission / realized P&L / time into `events.trade_fills` + the position's `events.position_events` lifecycle row (§15: BigQuery is the record; there is no Portfolio_Ledger.md / Decision_Log.md) — flipping ORDER-STAGED→OPEN or exit-pending→CLOSED. Multi-session fills (a persist-and-wait order re-crafted DAY across several sessions, or any legacy/operator-placed GTC still working) and exchange-split partial fills (aggregate by `order_id`) are caught by the window. The "PROVISIONAL fill / reconciliation owed to a screenshot session" failure mode is structurally eliminated. **The same reconciling-fill pass also resolves any `termination_close_staged` / `position_reconciliation_lag` alert the fill closes** — the exact match conditions are the AUTHORITATIVE inline clauses in Claude_Task_Plan.md's D2a "STEP 0 — BROKER RECONCILIATION" section (not restated here to avoid a second copy drifting out of sync — a prior copy living only in Claude_Task_Plan.md's non-canonical "IBKR connector usage" summary, never here or in D2a's own bullet list, is why `position_reconciliation_lag` silently never auto-resolved for six weeks; fixed 2026-07-21).

## 12. Queue Lifecycle and Daily Archive Policy

**Canonical-current text:**

The two drain-to-completion queues — `PENDING_ANALYSIS` (drained daily by D2) and `PENDING_REVIEW` (drained by the Adversarial Review routines) — are cleared **daily**, not on a retention window. They are represented by latest-state rows in `state.open_queue` over append-only `events.queue_events`; a terminal row drops an item from the live view. Rationale: unlike the append-only decision history, a queue is read **to completion** every day by its drainer, so a completed entry left actionable would be needlessly re-read each day.

Each day **D3 Calendar Hygiene** sweeps every entry at a terminal `status` (`complete`/`superseded`) out of its live queue into the queue's daily archive (`Archived_Analysis.md` / `Archived_Adversarial_Reviews.md`): the full block is appended (tagged with an `archived:` date) and then removed from the live file entirely — **full clear, no pointer line** (this differs from the Decision_Log archive, which leaves a pointer). The live queue retains only actionable entries (`pending`, plus the adversarial queue's in-flight `recommendation-complete` / `attacker-complete`) plus its header/schema preamble.

Lookup: an id absent from a live queue has a terminal-status row in `events.queue_events` (no `.md` archive — §15). The durable verdict/outcome record lives independently in `events.adversarial_reviews` (the review transcripts) and `events.decision_log` / `state.current_regime` (the retired per-review `Adversarial_Review_*.md`, Regime_State.md, and Decision_Log.md are BigQuery now, §15) — gates needing a completed review's result read those, not the queue.

Read-access: the daily archives are append-only cold traceability; Daily/Weekly routines do not read them for decision input (D3's mechanical sweep-append is exempt). Monthly+ cadence may read them (Q1 reads the adversarial daily-archive for prior-quarter review records).

Authoritative procedural details (the D3 sweep step, append-only file-write convention): see Claude_Task_Plan.md "Queue lifecycle and daily archive policy" and §D3.

## 13. Account-Level Cash/Park Reconciliation, Drift Attribution & Cash Flattening

The five strategy sub-portfolios share one IBKR account; undeployed capital sits in the **park** — the shared idle-capital vehicle, **SGOV from account inception through the 2026-07-15 cutover, VOO from that transfer forward** (owner directive 2026-07-15; `state.park_policy_current` always names the CURRENT vehicle — see below). The connector has no A/B/C/D/E buckets. **The park is account-level and is NOT split per strategy** (a hand-kept per-strategy park-share ledger is dissolved as of 2026-06-19 — `events.parking_events.strategy` is NULL on every row, so the park has no strategy tag and never had a reconcilable split): the **total** park holding is event-sourced in `state.park_reconciliation` (net shares + cash from `events.parking_events`, filtered to the CURRENT vehicle via `state.park_policy_current`; the A.1 reconciliation basis), and per-strategy **budget** comes from `analytics.strategy_nav` (`available_funds` / `sizing_base_2pct`), which is NAV-derived and never needed a park-share ledger. Account-level events that are NOT strategy trades — cash dividends, interest, account fees, deposits/withdrawals, and operator-initiated cash operations (e.g. the operator selling park shares to clear a negative cash balance left by accumulated commissions) — change live cash/park without, by themselves, telling Claude which strategy they belong to. This protocol detects that drift and attributes it deterministically so per-strategy budgets stay correct. It runs as part of D2 Step 0, every daily run, before any sizing or staging.

**Which vehicle is "the park" right now?** `SELECT vehicle, effective_date FROM state.park_policy_current` — event-sourced from `events.park_policy_changes` (`bigquery/54_park_policy_voo_cutover.sql`), NOT a hardcoded literal in this file. Cached `contract_id`s: **SGOV 424099317**, **VOO 136155102** (ARCA, US primary listing — resolved 2026-07-15 via `search_contracts`; also cached in Claude_Task_Plan.md's contract_id list). Every step below that references "the park" or "park shares" means whichever vehicle `state.park_policy_current` currently names — read it once per D2 Step 0 run, not once per session.

**Historical note (do not rewrite):** `events.parking_events.ticker` distinguishes which vehicle each row parked into — every row before 2026-07-15 is genuinely `'SGOV'` (backfilled, not reinterpreted); `state.sgov_position`/`state.sgov_reconciliation` are FROZEN to that SGOV-only history and no longer the live reconciliation basis (superseded by `state.park_position`/`state.park_reconciliation` below, which follow the current vehicle).

**Invariant (the accounting target).** All undeployed capital lives in the shared park; account USD cash is held at ≈ $0 (within the no-act band in E). Consequently each strategy's **available (undeployed) funds = its park-allocation value + its (near-zero) cash residual**, and summing across strategies: **Σ available funds = total park market value + total USD cash = total undeployed NAV**, with the **event-sourced total park shares** (`state.park_reconciliation.events_park_shares`) matching the connector's park-vehicle share count (the reconciliation basis in A.1) — no per-strategy park-share split is kept or required. **Commission model — SGOV (empirical — IBKR fractional SGOV).** Per-order commission = `min(1% × trade_value, $0.35)`: a flat **1.00% of trade value below ~$35**, then a flat **$0.35 from ~$35 up to ~$100** (above which the $0.0035/share tiered rate re-exceeds it — irrelevant at fractional sizes). Confirmed across the SGOV fills in `get_account_trades` (e.g. $10.06→$0.101, $23.14→$0.232, $30.13→$0.302, $35.18→$0.351, $38.24→$0.351, $40.16→$0.350). There is **no fixed $0.35 minimum** on small fractional orders — the 1%-of-value cap overrides it. Because commission (1%) and SGOV's yield (~4%/yr) both scale with the amount, SGOV's parking break-even is **amount-independent ≈ 3 months of dwell** (1% ÷ 4%).

1. **Balances to act on.** `settled_cash` = settled USD cash (`get_account_balances`). `free_cash = settled_cash − Σ reserved_cash − Σ open_withdrawal_candidates` over the **staged-order registry** `state.open_orders` (its `reserved_cash` column = qty×limit + est. commission for each still-`pending` BUY entry; resting SELL exits reserve nothing) **plus** any live unfilled BUY in `get_account_orders` / `get_order_instructions` not already represented there. The **sweep** test (3) uses `free_cash` — never sweep cash a pending buy will consume. The **cover** test (4) uses `bridge_adjusted_settled_cash` (defined in step 4 — NOT raw `settled_cash`, which during a paired-rotation settlement window reads a debit of order the whole switch notional) — cover only a *realized, unfunded* debit; do NOT pre-fund a resting limit buy that may not fill. A buy placed against ~$0 cash is allowed to fill into margin (the park holding is the collateral) and the realized negative is cleared on the next sweep. The SWEEP's own sizing still never pre-counts pending SELL proceeds — a sweep parks *idle* cash, and cash that has not landed is not idle — but see the paired-rotation exception immediately below.

   **OPEN-WITHDRAWAL-CANDIDATE HOLD (`bigquery/161_withdrawal_after_the_fact.sql`, owner directive 2026-08-10).** `Σ open_withdrawal_candidates` = `SELECT COALESCE(SUM(ABS(amount)),0) FROM state.cash_flow_candidates_open WHERE direction='WITHDRAWAL'`. Cash the previous session flagged as probably leaving the account is NOT free cash: sweeping it into the park would force the operator to sell the park again, or to decline a confirm-tap they should never have been shown. This hold is written by the routine itself from connector evidence, never declared by the operator in advance — it is the after-the-fact discovery doing double duty as the sweep guard. It clears automatically the moment the candidate is confirmed (the money is gone, so `settled_cash` already reflects it) or retracted (it was a hold, so the cash is genuinely free again). **Also skip the sweep for one cycle when this session observed a park SELL it did not itself craft** (a `get_account_trades` park-vehicle SELL with no matching `state.open_orders` row): an operator raising cash by hand is the leading indicator of a withdrawal this system has not yet seen, and idling that cash for one cycle costs nothing while re-parking it costs a round trip. Note the sweep already reads SETTLED cash, so T+1 settlement gives roughly a day of natural cover on top of this.

   **PAIRED-ROTATION EXCEPTION — settlement bridging, NOT leverage (owner directive 2026-07-26).** A BUY that is the paired second leg of a capital rotation MAY be sized off the EXPECTED net proceeds of its own in-flight SELL, before those proceeds settle, subject to all four of: **(a)** the funding SELL is already crafted and staged in `state.open_orders` **this session** — never a hypothetical, future, or merely-intended sale; **(b)** `buy_cost ≤ free_cash + Σ (expected_net_proceeds(paired SELLs) × 0.995)`, where `free_cash = settled_cash − Σ reserved_cash(OTHER pending BUYs)` per this step — the base is **`free_cash`, never raw `settled_cash`**, so a rotation can never consume cash an already-staged entry has claimed (that would silently re-create the 2026-06-08 MDT de-funding this registry exists to prevent), and gross exposure never rises and the transient margin loan nets to ≈ 0 — this authorizes **bridging settlement, never leverage**, and a BUY exceeding that bound is simply sized down to it; **(c)** expected proceeds are haircut **0.5%** for open-gap slippage and both legs are MARKET/DAY, so the residual lands slightly positive in the base case (`buying too much is still the failure mode to avoid`, step 3); **(d)** the two legs name **different tickers** — a same-ticker pair is a PDT day-trade, so defer it per the day-trade guard instead. Why: with market-only orders (owner directive 2026-07-21) a fill is near-certain, and the account is margin-enabled, so waiting a session for settlement bought nothing except a session of unintended exposure to the very vehicle the AI had just decided to leave. Any resulting transient debit is an EXPECTED residual under C's paired-rotation branch, never an unexplained one; a debit left by a rotation whose funding leg did NOT fill is a different thing entirely and escalates per that branch.

   **MARGIN AUTHORIZATION (owner directive 2026-07-26 — stated explicitly because nothing in this repo previously sanctioned margin borrowing at all).** The account is margin-enabled, and this protocol now authorizes margin use for EXACTLY ONE purpose: bridging settlement on a paired rotation, bounded by the step-1(b) test so the loan nets to ≈ 0 once both legs settle. This extends the long-standing small-debit tolerance in step 4 ("a debit between $0 and −$5 is intentionally left on margin") from an incidental rounding artifact to a deliberate, bounded, self-extinguishing bridge. It is NOT authorization to lever the book: no position may be opened that gross exposure cannot cover once in-flight legs settle, there is no approved margin-financed entry outside a paired rotation, and a margin balance that OUTLIVES its settlement cycle is by definition a broken rotation (C's escalation clause), not a funding strategy. PDT still binds independently — the account sits under the $25k threshold, so same-TICKER round trips remain limited and are deferred via `day_trades_remaining`; a cross-ticker rotation is not a day trade and is unaffected.
2. **No-act band.** Take no action when `free_cash < +$25` (no sweep) **and** `bridge_adjusted_settled_cash > −$5` (no cover — see step 4; the raw `settled_cash` figure is NOT the cover input while a paired rotation is mid-settlement). The $25 floor is a **pragmatic** trigger — operator-tap friction (§11) and IBKR's fractional min-order size — **not** a commission break-even; this rationale is unchanged by the vehicle switch (see the VOO commission-model note above on why the break-even itself moves, without changing the floor). The sub-band residual is left as tracked cash (attributed per C) and clears on the next qualifying cycle.
3. **Sweep (free_cash ≥ +$25 → BUY the current park vehicle).** Size DOWN so cost + commission can never overdraw: `shares = floor_to_4dp((free_cash − comm_buffer) / park_ask)`, where `comm_buffer` is the current vehicle's actual per-order commission (SGOV: `min(0.01 × free_cash, $0.35)`; VOO: per the UNVERIFIED note above until confirmed from live fills) — exact rather than a flat reservation, so a small sweep no longer strands residual otherwise-parkable cash. For safety against price drift between estimate and fill, take the larger of this estimate and the connector's latest per-order commission for that vehicle from `get_account_trades`. **Buying too much is the failure mode to avoid** — a tiny positive cash residual is fine.
4. **Cover (bridge-adjusted settled_cash ≤ −$5 → SELL the current park vehicle).** **BRIDGE ADJUSTMENT FIRST — MANDATORY (owner directive 2026-07-26; this is a HARD SAFETY RULE, not a refinement).** Before testing the cover threshold, compute `bridge_adjusted_settled_cash = settled_cash + Σ expected_net_proceeds(paired SELLs that have FILLED but not yet SETTLED)`, reading the filled-but-unsettled legs from `get_account_trades` / `state.open_orders`. **Test THAT figure against −$5, never raw `settled_cash`.** Why this is mandatory: under the paired-rotation exception (step 1), the incoming vehicle's BUY deliberately fills on margin before the outgoing vehicle's SELL proceeds settle (T+1). Raw `settled_cash` therefore reads a large realized negative — of order the full switch notional — for one settlement cycle. A cover sized off that raw figure would **SELL the brand-new policy vehicle to clear a debit its own paired SELL is already about to extinguish, partially unwinding the very switch just executed** — the single worst failure mode this redesign can produce, converting one intended rotation into two unintended round-trips plus commissions. The bridge adjustment nets the in-flight proceeds back in, so the test sees the true economic deficit (≈ 0 for a well-sized rotation) rather than the settlement artifact. A debit that survives the adjustment is genuinely unfunded — cover it normally, and if it corresponds to a rotation whose funding leg did NOT fill, escalate per C's broken-rotation clause. Then, sized on that adjusted figure: size UP so net proceeds fully clear the *realized* debit and leave no margin balance: `shares = ceil_to_4dp((|bridge_adjusted_settled_cash| + comm_buffer) / park_bid)` (`comm_buffer` per step 3), capped at the available park holding (if a deficit ever exceeded the park holding — not the case at current scale — sell all of it and flag the residual margin in chat + Decision_Log). **Selling too little is the failure mode to avoid** — a tiny positive cash residual after covering is fine. A debit between $0 and −$5 is intentionally left on margin (covering it would cost more commission than the trivial daily margin interest); it clears once it deepens past −$5 or a positive cash event (dividend / exit proceeds) nets it out.
5. **Craft it.** `create_order_instruction(contract_id <current vehicle's, per the table above>, side, quantity=shares, order_type='MARKET', time_in_force='DAY'` per §11) — **no `limit_price` argument is transmitted to IBKR** (market-only, owner directive 2026-07-21). Record the live reference price (last, or bid/ask mid, from `get_price_snapshot`) in the staged payload's `limit_price` field for cash-reservation only — it is not an order limit. **Order-guard check first** — `SELECT * FROM analytics.fn_order_guard(NULL, side, shares, ref_price, 'MARKET')` (`bigquery/104_strip_pretrade_rails.sql`, which supersedes `bigquery/100_market_only_order_guard.sql`'s guard call — owner directive 2026-07-22 strips every remaining liquidity and sizing rail; park orders now get the identical market-only + qty/ref-price sanity check as any other order, with no separate NAV-based backstop). Record the instruction `id` in the `state.open_orders` registry — **do NOT insert a `events.parking_events` row yet** (see the CONVENTION FORWARD note in step 6: a pending sweep/cover lives solely in the `state.open_orders` registry until it fills). `create_order_instruction`'s own IBKR notification is the confirm surface for the sweep/cover (2026-07-09 calendar-scope narrowing, §1 — no calendar event for a craftable park order); a `[Claude] Confirm order` event with the deep link + `SIDE QTY <TICKER> TYPE DAY` summary (`TYPE` is always `MARKET`) is created only if the park order is ever non-craftable.

## 16. Strategy Termination, Kill-Trigger Detection & Capital Redistribution

**Operational-protocol index for the capital-growth / survivorship model (2026-06-01 owner pivot).** The canonical *capital-model* spec lives in **Experiment_Parameters.md** ("New strategy funding (probe stake)", deposit-allocation order, strategy-termination definitions) and the *cadence wiring* lives in **Claude_Task_Plan.md** (D1/D2/M5 prompt bodies); this section is the single operating-protocol pointer so a routine can find the rules without re-deriving them.

**Capital model (canonical: Experiment_Parameters.md).** The system is a live capital-growth engine, not a frozen forward-test: scale capital and let each thesis choose its own no-ceiling risk budget through the seven-factor justification plus mandatory adversarial size attack; reward winners *passively* via survivorship, not by merit-weighting a short, noisy sample.
- **Probe-stake floor $2,000** (adjustable): a newly-added strategy starts frozen (defined, zero booked allocation, non-trading) and accumulates until its booked allocation reaches $2,000. The floor avoids commission-dominated deployment at the account's operating scale; it neither prescribes a position fraction nor implies a fixed-dollar order. Every PROBE entry is instead sized under the no-ceiling per-thesis discipline (seven-factor justification plus mandatory adversarial attack on size). Below the floor it never trades at commission-dominated size.
- **Inflow priority (deposits AND sunset-redistribution):** fill pending newcomers to the floor FIRST — oldest-pending first (FIFO), one filled before the next — then the AI CAPITAL-ALLOCATION CALL below allocates the remainder among the **capital-ENABLED, NON-NOMADIC** active strategies (rev 2026-07-19 evening, REGIME-CAPITAL SYNC below — a regime-router DO-NOT-ACTIVATE strategy is capital-disabled and receives zero; this REVERSES the same morning's Redesign-A "including router-deactivated ones" wording; **NON-NOMADIC added 2026-08-11, NOMADIC STRATEGY CAPITAL below** — a strategy declared at ≤1 trade/month holds no exclusive capital by design and must never be handed a deposit/redistribution share it would just need sweeping back out on the next pass). Not a one-time carve; newcomers have first claim on every inflow until filled. No held-aside pool — terminated capital always redistributes to survivors.
- **Redistribution on termination:** a terminated strategy's booked allocation auto-redistributes per the order above — **no adversarial review, no hold option**, unchanged by the AI call below (the judgment is only ever *how much* each survivor gets, never *whether* to redistribute or *whether* to hold). Capital sits in the park (§13 — SGOV historically, VOO from the 2026-07-15 cutover forward) until a survivor stages a separately justified thesis, so redistribution changes *booked allocation*, not immediate exposure; no preset fraction or deployment pace applies.
- **Retired by this pivot:** the `capital-redistribution` review type, the dedicated **Recommendation routine** (the only former three-routine pipeline), the `recommendation_due_date`/`recommendation_output_path` fields, the `recommendation-complete` status, and the held-aside pool.

**The AI capital-allocation call (owner-approved redesign 2026-07-19 — `AI_DECISION_REDESIGN.md` §3 Redesign A).** The remainder after the mechanical PENDING-NEWCOMER floor fill above is no longer a fixed equal split — the session already executing the event (D2 step 5's termination handler, AR_orc's m2m-termination handler, or the §13.C deposit-recording flow) makes the call, structured and auditable exactly like the park allocation call (§13.F):
- `allocations` — one {`strategy_code`, `pct`, `dollars`} entry per currently-active survivor, `pct` summing to 100
- `conviction` — HIGH / MEDIUM / LOW + a numeric `conviction_pct`
- `rationale` — one paragraph addressing why the top-allocated survivor (`winner_code`) beats the runner-up (`runner_up_code`)
- `invalidation` — the observable development that would flip this call
- `theater_check` — a one-line self-audit that the rationale isn't narrating a foregone conclusion

**Rails (mechanical — bound the call, never choose it). This subsection is the CANONICAL rail text — D2 §5, AR_orc, and §13.C point here; on any wording divergence, this text governs:**
- Each survivor's dollar share must fall within **[0.5×, 2×] its equal share** (never $0). **Band-fitting algorithm (fixed, 2026-07-19 review F3):** clamp every out-of-band share to its nearest band edge; redistribute the resulting surplus/deficit **proportionally across the surviving UNCLAMPED shares only**; repeat until no share is out of band (this converges — each pass clamps ≥1 more share, and all-clamped-at-edges is itself a valid in-band allocation). **Assert `SUM(dollars) = residual ± $0.01` after fitting**; if the assertion fails or the fit degenerates, fall back to DEFAULT-EQUAL and record why.
- **Default-EQUAL below MEDIUM conviction** (or on a HOLD/no-call, or on any rail failure above): apply the classic equal split instead — for a **deposit**, the single `strategy` NULL `events.cash_flows` row exactly as before; for a **termination**, equal per-survivor amounts through the same double-entry write below.
- **Termination write path (fixed, 2026-07-19 review F2 — the concrete mechanism, replacing the former vague "reconcile in the events-side state" language):** the terminated strategy's booked remainder moves via **`events.cash_flows` double-entry on one flow_date** — one `strategy`-tagged **negative** row for the terminated strategy (−remainder) and one `strategy`-tagged **positive** row per recipient (the fitted or equal amounts, summing to +remainder) — so account-level `SUM(amount)` is unchanged (an internal transfer, not a deposit) and `analytics.strategy_nav` mechanically moves the capital into each survivor's NAV/2%-sizing base. The newcomer floor-fill portion of the same event uses the identical double-entry (its positive rows to the newcomers, netted in the same negative row). Deposits are genuinely new money — positive rows only, no offsetting debit. **`source='termination_redistribution'` on EVERY row of the event** (the single negative row and every positive recipient row, including any newcomer floor-fill rows netted into it) — specified 2026-08-10, `bigquery/163_cash_flow_source_provenance.sql`, closing a gap where this write path named no `source` at all in any of its three descriptions and would therefore have silently inherited the column DEFAULT. **REGIME-CAPITAL SYNC (owner directive 2026-07-19 evening — reverses the same morning's Redesign-A "including router-deactivated ones" stance; canonical rails HERE + §13.C; schema `bigquery/98_regime_capital_enablement.sql`).** A strategy DISABLED for unfit market conditions (regime-router DO-NOT-ACTIVATE) receives **zero capital allocation**, and its previously allocated capital **redistributes to capital-enabled strategies** — explicitly distinct from an active strategy that is merely idle (no opportunity / insufficient budget), which keeps its capital.
- **Predicate (`state.strategy_capital_enablement`):** a roster-active strategy is `capital_disabled` iff its latest `events.regime_events` `STRATEGY_ACTIVATION` row with `event_ts` **before today** (America/Denver — a 1-session before-today cutoff, so a same-day router flip never triggers a same-session capital move) reads DO-NOT-ACTIVATE; otherwise `capital_enabled`.
- **SWEEP (mechanical weight, 2026-08-11; formerly judgment-or-equal):** when a capital-disabled strategy holds `available_funds ≥ $25`, the full amount sweeps to the capital-enabled strategies, recorded as an atomic $0-sum `events.cash_flows` double-entry on one flow_date tagged `source='regime_capital_sweep'` (one negative row for the disabled strategy, positive rows per recipient). **The recipient SET comes from `state.regime_capital_sync_pending` itself (`bigquery/168` FIX 7: `capital_enabled AND NOT nomadic`); only the SHARES come from `state.sweep_recipient_weights`** (`bigquery/164_capital_utilisation_and_restore_integrity.sql`, superseded by `bigquery/202_sweep_recipient_weights_nomadic_exclusion.sql`, which gave the weight view that same nomadic exclusion so the two predicates match by construction): each recipient takes `ROUND(swept_amount × sweep_share, 2)`, last row absorbing the rounding penny. The weight view is a capacity TILT among already-eligible recipients and is NEVER the eligibility authority — bigquery/164 predated the nomadic concept by hours and carried no nomadic term, so reading the set from it credited nomadic C on 2026-08-12 and 2026-08-18, against the NOMADIC STRATEGY CAPITAL rule below that a nomadic strategy holds no exclusive standing capital ever (`ops.alerts` `sweep_recipient_view_drift`, raised by D2a 2026-08-27). **Why this changed:** the previous rule routed through the AI CAPITAL-ALLOCATION CALL above (`trigger='regime_disable'`, [0.5×, 2×]-of-equal-share rails, default-EQUAL below MEDIUM) — but D2a, the only routine that executes a sweep, *carries no analysis by design* and therefore can never clear the MEDIUM-conviction bar, so in unattended operation EVERY sweep was an equal split. Measured 2026-08-11: both autonomous sweeps (2026-08-05, 2026-08-06) took DEFAULT-EQUAL; the sole tilted sweep (2026-07-19) ran in an interactive session on owner instruction. The weight closes that structurally — it is arithmetic over deployment history (share of the trailing 180 days each recipient actually held a position), needs no judgment, and is **already inside the [0.5×, 2×] band by construction** (`band_multiplier` is clamped in SQL before normalisation), so no band-fitting pass applies. It keys on **deployment capacity, never on P&L** — merit-weighting a short noisy sample stays rejected per the capital-model principle above — and it **degenerates to exactly the equal split when recipients are indistinguishable**, so it can never be worse than the behaviour it replaces. An AI call remains permitted where a session genuinely has analysis (a termination or deposit handled by D2/AR_orc); DEFAULT-EQUAL remains the fallback if the weight view is empty or its shares do not sum to 1.0.
- **RESTORE (mechanical, debt-tracked — NO AI call):** `state.regime_capital_debt` tracks each strategy's swept-out total minus restored total. When a debtor strategy flips back to capital-enabled, its outstanding debt restores from the other enabled strategies **pro-rata by their `available_funds`** (capped at donor capacity; ≥$25-or-full-debt floor), as a `source='regime_capital_restore'` double-entry (`trigger='regime_enable'` context). Restore is owed-money mechanics, not judgment.
- **Executor + surface:** D2a Step 0's REGIME-CAPITAL SYNC substep (Claude_Task_Plan.md) reads `state.regime_capital_sync_pending` (pre-computed SWEEP/RESTORE rows + equal-share/pro-rata baselines) and executes **ONE movement per read** — re-read the view after every write before acting again (fix for the multi-RESTORE stale-snapshot defect found in the 2026-07-19 adversarial review). The first sweep (A capital-disabled — DO-NOT-ACTIVATE confirmed since 2026-07-01; $1,889.37 → B/C/D/E at 30/22.5/30/17.5, MEDIUM 60%) was executed in-session 2026-07-19 on owner instruction.
- **Kill-switch:** `ops.capital_control` (append-only; latest row wins via `state.capital_control_latest`; seeded `enabled=TRUE`). `enabled=FALSE` → the D2a substep records what it would have moved and moves nothing. Deposit routing (§13.C) is unaffected by this switch.
- **DEPOSIT × CAPITAL-DISABLED INTERACTION — the equal-split default is NOT neutral, and the round-trip below is EXPECTED (documented 2026-08-05 at D2a's own request, after the first deposit to occur while a strategy was capital-disabled).** A deposit D2a cannot form a MEDIUM+ conviction call on is recorded as a single `strategy` NULL `events.cash_flows` row (§13.C) — and NULL means equal-split across the **whole roster**, including any capital-disabled strategy. So the deposit mechanically funds a strategy this section says must hold zero, and the SWEEP above then pulls it straight back out **in the same session**. Worked example, 2026-08-05: a $9,995.39 deposit handed capital-disabled Strategy A its 1/5 share of $1,999.08, which swept back out and redistributed as $499.77 to each of B/C/D/E — net $0 to A, correct final state, reached via a transient allocation that never should have existed. **Do NOT "fix" this by suppressing the sweep or by special-casing the disabled strategy inside the sweep — the sweep is what makes the outcome right.** The transient is a property of NULL meaning "equal across the roster" while enablement is evaluated separately and afterward. If a future pass wants to remove the round-trip rather than merely document it, the correct place is the deposit-recording flow in §13.C (record the NULL default across capital-ENABLED strategies only), not this section — and that change must preserve the `state.regime_capital_debt` accounting, since a share never allocated is not a share swept and must not register as debt owed back.
- **Invariants:** account-level `SUM(amount)` unchanged (internal transfer, not a deposit); kill/gate/TWR flow-immunity re-verified (book-drawdown `cum_flows` invariance verified live); a TERMINATED strategy's outstanding regime-capital debt is extinguished (the survivorship redistribution above already disposes of its capital).

**NOMADIC STRATEGY CAPITAL (owner directive 2026-08-11, redesigned same day — supersedes the same day's first-draft "CAPITAL DORMANCY SWEEP"; canonical rails HERE; schema `bigquery/167_nomadic_capital.sql`, which supersedes `bigquery/166_capital_dormancy_sweep.sql` in full).** A capital-ENABLED, roster-active strategy declared at **≤1 trade/month** by its own `strategy/0N_*.md` "Declared expected frequency" section is classified **NOMADIC** — currently C and D, FALSE for A/B/E (`state.strategy_declared_frequency.is_low_frequency_by_design`, unchanged from the first draft). This is a **PERMANENT, structural classification**, not a conditional "currently looks idle" state — the first draft gated eligibility on ≥90 days since deployment plus recent evaluation activity; the redesign drops both gates (a strategy is nomadic or it isn't, independent of when it last traded) and keeps only the one structural guard that must never be relaxed: **no open position** (never sweep capital out from under a live trade). A NOMADIC strategy holds **NO exclusive standing capital, not even a reserve floor** (the first draft kept $2,000 back; retired — there is no "at rest" balance for a permanently-nomadic strategy that isn't $0). It borrows what a thesis needs, proportionally from the other enabled strategies, at the moment it needs it, and returns it when the position closes. Two facts keep this an accounting-only move, not a new settlement mechanism: the five strategies already share one IBKR account (§13 — `available_funds` is a bookkeeping split of one pooled cash balance, not a segregated sub-account), and position sizing has carried no NAV-based ceiling for any strategy since the 2026-07-22 pre-trade-rail strip (`bigquery/104`) — **size is determined ENTIRELY by the AI's normal seven-factor risk-budget judgment, same discipline every strategy's sizing already carries; this mechanism sources whatever that judgment calls for, it does not cap it.**
- **SWEEP (mechanical, standing condition, D2a-executed daily):** a nomadic strategy's idle balance sweeps to the currently-**non-nomadic** capital-enabled strategies, split **plain pro-rata to each recipient's own `available_funds`** (owner directive: "borrows proportionally from all other enabled strategies," applied symmetrically to the sweep-out direction too — simpler than and replaces the first draft's capacity-weighted tilt borrowed from the regime sweep). Tagged `source='nomadic_capital_sweep'`. Two bounds on "idle balance," both added by `bigquery/168` after audit: it is **net of `state.open_orders.reserved_cash`** (cash a pending staged BUY already needs is never swept — the same rule §13 applies to the park sweep, for the same 2026-06-08 MDT de-funding reason), and a **≥$25 de-minimis movement floor** applies, the same figure the regime sweep uses. The $25 is a minimum transfer size to avoid dust ledger rows, **not** a retained reserve — below it the balance simply waits for the next pass. There is no $2,000-style reserve floor; that was the superseded first draft. The sweep double-entry is exactly $0-sum by construction (the view's last recipient absorbs the rounding residual). If a nomadic strategy has capital to sweep but every capital-enabled strategy is itself nomadic, the view emits a `blocked_no_recipient` row rather than going silently empty, and D2a raises `nomadic_sweep_blocked` instead of mistaking it for the healthy steady state.
- **BORROW — on-demand only, NOT a standing daily condition (the one deliberate divergence from the regime-sweep pattern above, unchanged from the first draft's reasoning).** Regime RESTORE fires on a state transition (re-enablement) genuinely independent of same-day trading intent; a nomadic strategy has no equivalent transition — it stays capital-enabled throughout — so a daily standing pull-back would simply reclaim the swept capital the moment any donor has spare cash, which is most days, defeating the sweep within a session or two. Instead: the order-craft step for a nomadic strategy's GO thesis calls `analytics.fn_nomadic_capital_restore_plan(p_strategy, p_amount_needed)` **at the moment the AI-sized risk budget exceeds current `available_funds`**, which pulls `LEAST(amount_needed, total donor capacity)` pro-rata from the same non-nomadic donor set. **NOT capped by this strategy's own sweep history** (the first draft capped BORROW at `outstanding_debt` — a receivable-return model; the redesign removes that cap, since size is the AI's call, not a function of how much this strategy has ever had swept from it — see the schema file header for the full reasoning). Tagged `source='nomadic_capital_restore'`; MECHANICAL, no AI call.
- **Ledger (`state.nomadic_capital_ledger`):** tracks `swept_out_total - restored_total` per strategy as `net_position`, which — unlike the regime-capital debt it structurally mirrors — **can go negative**: a nomadic strategy that borrows more than it has ever had swept from it now owes its own future proceeds back to its lenders, not merely "its own money." A strategy's OWN realized P&L still accretes to its tracked `analytics.strategy_nav.nav` exactly as before this mechanism existed — nothing here changes how a strategy's edge is measured for kill-trigger/30-trade-gate/TWR purposes; what changes is that the cash backing that NAV never sits idle in its own bucket.
- **Excluded from the JUDGMENT capital-inflow paths — but NOT from the default-equal deposit path (stated honestly, because the two differ).** The AI CAPITAL-ALLOCATION CALL above allocates only among capital-ENABLED, NON-NOMADIC active strategies (INFLOW PRIORITY bullet amended accordingly), and `state.regime_capital_sync_pending`'s SWEEP recipient set (`bigquery/98`, redefined by `bigquery/167`/`bigquery/168`) also excludes nomadic strategies — without that, a router-disabled strategy's regime sweep would route a share to a nomadic strategy that just needs sweeping right back out next pass. So a below-MEDIUM deposit DOES transiently hand a nomadic strategy a share, which the next daily sweep then removes — exactly the same documented transient-then-swept round-trip the DEPOSIT × CAPITAL-DISABLED bullet above describes, and correct in its final state for the same reason. Do not "fix" it by special-casing the sweep; if a future pass wants to remove the round-trip, the correct place is §13.C's deposit-recording flow, and it must preserve the ledger accounting (a share never allocated is not a share swept and must not register as owed back).

- **Kill-switch:** `ops.capital_nomad_control` (append-only; latest row wins via `state.nomadic_capital_control_latest`; seeded `enabled=TRUE`) — separate from `ops.capital_control` (the regime-sync switch), so either mechanism can be paused independently.

**Steps:**

1. **Query `ops.run_log` for completed sessions in the last 36h.** Execute (read-only):
   ```sql
   SELECT DISTINCT session_id, branch, routine, run_date
   FROM ops.run_log
   WHERE status = 'completed'
     AND log_ts >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 36 HOUR)
     AND branch IS NOT NULL
   ```

2. **Test each candidate for the stranded condition.** For each row in `candidate_sessions`:

## 20. Cross-File Citation Convention — Named Anchors, Not Line Numbers

**Canonical-current text:**

Every cross-file reference inside routine-executed prose (Claude_Task_Plan.md, this file, Strategy.md, Experiment_Parameters.md, Watchlist.md, Weekly_Catalyst_Calendar.md, the `task_plan/` slices, and any `ops/*.yaml` prose a routine reads) cites its target by a STABLE NAMED ANCHOR — a section heading, a rule name, a view/function/constant name, a decision_log title — never by line number (`File.md:1234`). This generalizes a rule first pinned narrowly to SL5's own handoff-contract payload spec (Claude_Task_Plan.md, STEP 0's RAISE-SIDE PAYLOAD CONTRACT, governing only its `producer_ref`/`consumer_ref` fields): "Prefer stable section anchors over line numbers in the two refs: this document's line numbers drift on every edit, and a heal that cannot find its own ref is indistinguishable from a contract that is still unpinned." That same block records SL5 measuring its OWN citations and finding 8 of 13 line pins had drifted within 3 days of being written — every `check_roster_consistency.py` pin shifted by exactly +30 lines after one insertion between two of the checks it cited — while every symbol those same pins named still resolved by grep, and it closes: "Do NOT re-add line numbers here." This section carries that same finding and that same rule to every cross-file reference in routine-executed prose repo-wide, not only to SL5's two fields.

**This is a measured finding, not a stylistic preference.** A repo-wide survey of `SomeFile.md:1234`-form citations found 41 of 51 (80%) stale. Roughly 10 of the 41 point at a literally blank line; the other ~31 — roughly three in four of the stale set — point at real but WRONG content: a heading, a divider, a neighbouring paragraph, or a different routine's section entirely. The repo has independently hit this and self-corrected twice already, each time by removing line numbers rather than re-pinning them: SL5's own 8-of-13 drift-within-3-days finding above (Daily.md), and a note in `ops/connector_tools.yaml` that drifted from `Claude_Task_Plan.md:345` to `:357` and was rewritten to cite its rule "by name, not by line number" — after which that replacement `:357` pin drifted AGAIN (the real content is now at `:623`). Two independent re-pin attempts, two repeat failures.

**The failure mode is SILENT.** Nothing in CI detects a stale line-number citation. A drifted citation still LOOKS like a citation — right filename, plausible-looking number — and because roughly three in four stale citations land on real, plausible content rather than an obviously blank line, neither a human reader nor a routine can tell a live reference from a dead one by looking at it. The number would have to be independently re-verified against the target file on every read, which is exactly the cost a stable anchor is meant to avoid.

**Decision: no CI gate for this, and none is planned.** The only mechanically-checkable version of the rule — flag a citation whose line number lands on a blank line — would catch only the ~10-of-41 blank-line cases (roughly a quarter of measured drift) while passing the majority of real drift (the ~31 pointing at wrong-but-plausible content) uncaught, which would give false confidence that the class is being caught when it mostly is not. It would also turn `main` red on landed, working history immediately, since ~10 existing citations already point at blank lines today and would all need fixing before such a gate could go green — the same reasoning this repo's operating guidance already applies elsewhere against adding a checker that fails CI on landed history for a cosmetic-relative-to-detectable defect.

**When a line number is genuinely unavoidable** (e.g., quoting a specific line of generated SQL, or citing a diff/stack-trace line), pair it with the named anchor so the reference self-heals when the number drifts — e.g. `bigquery/96_research_screener.sql:142 (inside the fields-JSON validation)`, not the bare line number alone.

**Existing stale citations are NOT being mass-re-pinned.** Re-pinning a stale line number to today's correct value reproduces the exact defect this section documents — it will drift again on the next edit to that file, as both prior re-pin attempts above did. Existing `File.md:NNN`-style citations convert to named anchors opportunistically, as each site is next touched for an unrelated edit — not as a dedicated repo-wide sweep.
